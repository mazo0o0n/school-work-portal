# خطة قياس الاستخدام والتكلفة

آخر مراجعة داخلية: 27 يوليو 2026.

هذه خطة مستقبلية فقط. لا تضيف tracking أو analytics أو جداول أو خدمات، ولا تعتمد أي تكلفة أو سعر دون قراءة الفواتير والخطط الفعلية.

## مبادئ القياس

1. قياس ما يساعد قرار منتج أو تكلفة محددًا فقط.
2. استخدام أحداث مجمعة وتقليل المعرفات والنصوص الخام.
3. عدم تخزين IP خام أو بصمة جهاز أو سؤال مساعد كامل لأغراض analytics.
4. الفصل بين القياس التشغيلي وسجلات الأمان وبيانات المنتج.
5. تعريف كل مؤشر وصاحبه ومدة الاحتفاظ قبل جمعه.
6. تحديث سياسة الخصوصية والتنبيه أو الموافقة عندما يتطلب الغرض ذلك.

| المؤشر | لماذا مهم | المصدر/مكان التخزين المقترح | يحتاج تنبيه أو موافقة خصوصية | الأولوية |
|---|---|---|---|---|
| المدارس المسجلة | يوضح حجم الوصول الأولي | عدّ مجمع من D1 `schools` | تنبيه الخصوصية عن التسجيل مطلوب | عالية |
| المدارس المتحققة | يفرق التسجيلات الجادة عن التجريبية | حالة التحقق في D1 | ضمن غرض الإدارة المعلن | عالية |

| تنزيلات التقارير | يثبت قيمة مكتبة Word | عداد حدث باسم التقرير والفترة دون أسماء أشخاص | يفضل إشعار شفاف | عالية |

| أخطاء المساعد | يراقب الاعتمادية والتكلفة | نوع الخطأ والمدة مجمعان | لا سؤال خام ولا stack trace | عالية |
| زمن استجابة المساعد | يربط الجودة بالتكلفة | مقاييس مجمعة p50/p95 | لا يحتاج هوية مستخدم | متوسطة |
| طلبات الدعم | يقيس عبء التشغيل | نظام دعم مستقبلًا | نعم؛ يتضمن تواصلًا ومحتوى | متوسطة |

## طريقة قياس تحافظ على الخصوصية

- استخدم معرف tenant داخليًا عند الحاجة، ولا تعرضه في تقارير عامة.
- اجمع العدادات حسب اليوم ونوع الحدث بدل حفظ كل نقرة دائمًا.
- افصل نصوص الأسئلة غير المجابة عن analytics العامة.
- ضع قائمة سماح لأسماء الأحداث والحقول؛ ارفض payload حرًا.
- لا ترسل أسماء المدارس أو الموظفين إلى أدوات تحليل خارجية.
- ضع حدًا لمدة الاحتفاظ وامسح الأحداث التفصيلية بعد التجميع.
- امنع analytics في صفحات الإدارة أو حقول الرموز والأسرار.
- وفر خيارًا واضحًا إذا أصبح القياس غير ضروري لتقديم الخدمة أو يتطلب موافقة.

## ما يمكن قياسه في D1 مستقبلًا

- عدادات تنزيل التقارير حسب `report_id` واليوم.
- عدادات نجاح وفشل التسجيل حسب `error_code` العام.
- عدادات أسئلة المساعد وfallback حسب اليوم دون نص السؤال.
- نشاط tenant مجمع مثل آخر يوم استخدام، بعد اعتماد الأساس والغرض.
- حدود الخطة والاستهلاك في SaaS.
- مؤشرات الدعم والحالة دون محتوى حساس في لوحة القياس.

لا يوصى بإنشاء جدول أحداث غير محدود قبل تعريف schema والاحتفاظ والفهارس والتكلفة. يمكن استخدام جداول تجميع يومية بدل سجل كل حدث إذا كانت الأسئلة التجارية لا تحتاج تفاصيل فردية.

## ما يمكن قياسه من Cloudflare Analytics

بحسب الخدمات والخطة والإعداد الفعلي، قد تتوفر طلبات المسارات، الاستجابات، الأخطاء، الزمن، استخدام Worker، وحركة Static Assets. يجب التحقق من لوحة الحساب والعقد قبل الاعتماد على أي مؤشر أو مدة احتفاظ. لا تُستخدم بيانات Cloudflare لاستنتاج مستخدم فردي أو ملف مدرسة دون غرض قانوني واضح.

## ما لا يجب قياسه

- كلمات المرور أو `ADMIN_API_TOKEN` أو رموز التعديل أو Bearer tokens.
- نص السؤال الكامل ضمن telemetry العام.
- بيانات دمج تقارير Word أو أسماء الموظفين.
- ملفات المستخدم أو محتوى Excel/CSV أو الصور التي تعالجها الأدوات.
- الهوية الوطنية والهواتف والبريد دون ميزة معتمدة تتطلبها.
- IP خام طويل الأجل أو بصمة جهاز أو موقع دقيق.
- محتوى localStorage/sessionStorage.
- metadata البحث الداخلي أو chunks أو scores في الإنتاج.

## خطة تتبع التكلفة

| بند التكلفة | وحدة القياس المقترحة | سؤال المراجعة الشهري |
|---|---|---|
| Cloudflare Workers | الطلبات، CPU time، الأخطاء | ما تكلفة كل ألف طلب وكل مدرسة نشطة؟ |
| D1 | القراءات والكتابات والتخزين | هل الاستعلامات والعدادات مجمعة ومفهرسة؟ |
| Vectorize | الأبعاد والمتجهات والاستعلامات والتحديثات | هل حجم المعرفة والاستعلامات يحقق قيمة قابلة للقياس؟ |
| Workers AI | عدد الطلبات/tokens أو الوحدة الفعلية في الفاتورة | ما تكلفة السؤال ونسبة fallback؟ |
| Static Assets/النقل | الطلبات وحجم النقل | ما الصور أو القوالب الأعلى استهلاكًا؟ |
| التخزين المستقبلي | GB-month والعمليات والنقل | هل R2 مطلوب فعلًا أم يمكن تأجيله؟ |
| البريد أو OTP مستقبلًا | الرسالة والتحقق والفشل | ما تكلفة المستخدم النشط ومنع الإساءة؟ |
| المراقبة | الأحداث والاحتفاظ والتنبيهات | هل التنبيهات تمنع خسارة أو وقت توقف؟ |
| الدعم | ساعات العمل والتذاكر | ما تكلفة دعم كل مدرسة وخطة؟ |

## تقرير تكلفة شهري مقترح

1. إجمالي تكلفة كل خدمة من الفاتورة الفعلية.
2. عدد المدارس المسجلة والمتحققة والنشطة وفق تعريف ثابت.
3. عدد أسئلة المساعد وتنزيلات التقارير والطلبات الكلية.
4. تكلفة المدرسة النشطة، السؤال، والتقرير المنزّل.
5. أعلى ثلاثة محركات تكلفة وأعلى ثلاثة أخطاء.
6. مقارنة شهرية لا تقل عن ثلاثة أشهر قبل اعتماد تسعير.
7. هامش احتياطي للنمو والدعم والضرائب والتقلب، يحدده القرار المالي.

## بوابة التنفيذ

لا يضاف أي كود قياس قبل اعتماد: اسم المؤشر، قرار المنتج الذي يخدمه، الحقول المسموحة، مدة الاحتفاظ، مسؤول الوصول، أثر الخصوصية، وطريقة الحذف. يبدأ القياس بتجربة مجمعة صغيرة، ثم يراجع قبل توسيعه.
