# خارطة طريق تأسيس SaaS

آخر مراجعة داخلية: 27 يوليو 2026.

هذه خارطة تخطيط فقط. لا تعتمد migration أو endpoint أو خدمة جديدة، ولا تعني الموافقة على تنفيذ SaaS.

## الوضع الحالي

- منصة ويب عربية منشورة عبر Static Assets وCloudflare Worker.
- تسجيل مدارس يحفظ اسم المدرسة والمرحلة وإدارة التعليم في D1، مع معرّف عام وحالة تحقق.
- لوحة إدارة للمدارس والأسئلة غير المجابة، محمية برمز إداري.
- خمس تقارير مدير Word قابلة للتعبئة في المتصفح.
- مساعد RAG يعتمد على معرفة معتمدة وVectorize وWorkers AI.
- أدوات محلية لإدارة التقارير والمعرفة والفحوص والجاهزية.
- بعض إعدادات المدرسة والتقارير والمحادثة تحفظ في `localStorage` أو `sessionStorage` على جهاز المستخدم.

## لماذا المشروع ليس SaaS كاملًا

وجود مدارس متعددة في جدول واحد لا يساوي تعدد مستأجرين. لا توجد هوية مستخدم، ولا عضوية تربط المستخدم بمدرسة، ولا سياق tenant موثوق يفرضه الخادم، ولا أدوار وصلاحيات على مستوى كل مدرسة. كذلك لا توجد اشتراكات أو حدود استخدام أو فوترة أو ملكية بيانات وحذف ذاتي أو مسار دعم تعاقدي.

## القدرات اللازمة

1. **الحسابات والمصادقة:** هوية مستخدم موثوقة، جلسات آمنة، واستعادة وصول.
2. **عضوية المدرسة:** ربط المستخدم بمدرسة واحدة أو أكثر بدعوة أو موافقة.
3. **عزل المستأجرين:** كل استعلام وكتابة يمران عبر `tenant_id` مستمد من جلسة موثوقة، لا من العميل وحده.
4. **الأدوار والصلاحيات:** حد أدنى مثل مالك المدرسة، مدير، عضو، ودعم داخلي.
5. **الاشتراكات:** حالة خطة مستقلة عن بوابة الدفع، مع تاريخ بدء وانتهاء وتجربة.
6. **حدود الاستخدام:** حدود واضحة وقابلة للتدقيق للتقارير والمساعد والتخزين.
7. **جاهزية الفوترة:** سجلات استحقاق واستهلاك وتسوية، قبل ربط مزود دفع.
8. **ملكية البيانات:** تحديد من يملك ملف المدرسة والتقارير والسجلات وكيف تُنقل أو تُحذف.
9. **مسار الدعم:** تذاكر أو قناة معتمدة، تصنيف أولوية، ومدة استجابة معلنة.

## v1.8.0 المقترحة: SaaS Foundation

### الهدف

بناء أساس هوية ومدرسة وعضوية وعزل بيانات صالح للاختبار، دون دفع أو خطط مدفوعة أو معرفة خاصة بكل مدرسة.

### الجداول المقترحة للمراجعة

| الجدول | الغرض | ملاحظة أمان |
|---|---|---|
| `tenants` | كيان المدرسة/المستأجر وحالته | معرّف داخلي مستقل عن الاسم والرقم الوزاري |
| `users` | هوية المستخدم الأساسية | أقل قدر من البيانات؛ قرار المصادقة يسبق التصميم النهائي |
| `tenant_memberships` | ربط المستخدم بالمدرسة والدور | قيد فريد على المستخدم والمدرسة ودور مضبوط |
| `tenant_invitations` | دعوات مؤقتة للانضمام | token مشتق/مشفّر، مدة صلاحية، واستخدام مرة واحدة |
| `tenant_settings` | إعدادات المدرسة غير الحساسة | لا تخزن أسرارًا أو بيانات أشخاص بلا حاجة |
| `usage_events` | عدادات تشغيل مجمعة | لا نصوص أسئلة ولا IP خام ولا معرفات تتبع تسويقية |
| `support_requests` | طلبات دعم مستقبلية | يطبق بعد سياسة احتفاظ وقناة دعم معتمدة |

هذه أسماء مقترحة وليست schema معتمدة. يجب إعداد نموذج تهديد ومراجعة علاقات الحذف والفهارس قبل أي migration.

### endpoints المقترحة

- `POST /api/auth/start` و`POST /api/auth/verify` وفق مزود الهوية المعتمد.
- `POST /api/auth/logout` لإنهاء الجلسة من الخادم.
- `GET /api/me` لإرجاع المستخدم والعضويات الحالية فقط.
- `GET /api/tenants/:tenantId` لملف المدرسة ضمن صلاحية العضو.
- `GET/POST /api/tenants/:tenantId/members` لإدارة العضوية بأدوار محدودة.
- `POST /api/tenants/:tenantId/invitations` وendpoint قبول الدعوة.
- `GET /api/tenants/:tenantId/usage` لإحصاءات مجمعة للمالك.

كل endpoint مقترح يجب أن يستخرج هوية المستخدم وعضويته من جلسة موثوقة، ويتحقق من tenant في الخادم، ويمنع الوصول الأفقي بين المدارس.

### الواجهات المقترحة

- الدخول والتحقق والخروج واستعادة الوصول.
- اختيار المدرسة عندما يملك المستخدم أكثر من عضوية.
- ملف المدرسة وإدارة الأعضاء والدعوات.
- صفحة صلاحيات مبسطة تشرح ما يستطيع كل دور فعله.
- صفحة استخدام مجمعة وحدود الخطة دون أسعار أو دفع في v1.8.0.
- مسار دعم بسيط بعد اعتماد سياسة الدعم والخصوصية.

### الاختبارات المطلوبة

- عزل tenant لكل قراءة وكتابة، بما في ذلك محاولات تغيير المعرّفات يدويًا.
- مصفوفة صلاحيات للأدوار والعمليات الحساسة.
- انتهاء الجلسة والدعوة ومنع إعادة الاستخدام.
- منع enumeration للحسابات والمدارس.
- قيود rate limiting وإجابات أخطاء لا تكشف وجود مستخدم أو مستأجر.
- حذف العضوية دون حذف بيانات المدرسة، وحذف tenant وفق سياسة معتمدة.
- اختبارات migration وrollback/backup وخطة استعادة.
- E2E للدخول، الدعوة، تبديل المدرسة، الخروج، والجوال.
- اختبارات وصول عربية RTL وأمن جلسات وCSRF حسب آلية المصادقة.

### المخاطر

- خطأ عزل واحد قد يكشف بيانات مدرسة لأخرى.
- تصميم هوية غير مناسب قد يفرض إعادة بناء لاحقة.
- جمع أسماء موظفين أو بيانات تواصل يرفع التزامات الخصوصية.
- ربط الخطط بالصلاحيات مبكرًا يخلط الأمن بالفوترة.
- migrations غير القابلة للعكس قد تعرض بيانات المدارس للخطر.
- تكلفة Workers AI وVectorize قد تنمو أسرع من الإيراد دون حدود.

## ما لا يجب تنفيذه الآن

- الدفع الإلكتروني أو التكامل مع مزود فوترة.
- معرفة RAG خاصة لكل مدرسة.
- R2 لقوالب مدفوعة أو مخصصة.
- RBAC معقد أو محرر صلاحيات حر.
- إعادة بناء الواجهة أو نقل التقنية دون سبب مثبت.
- جمع هواتف أو هويات أو بيانات طلاب لمجرد توقع استخدام مستقبلي.

## ترتيب التنفيذ المقترح

### v1.8.0 — SaaS Foundation

هوية، جلسة، tenant، عضوية، عزل، أدوار أساسية، واختبارات أمن.

### v1.8.1 — School Members

دعوات، إدارة أعضاء، تبديل مدرسة، سجل أحداث عضوية، وتجربة إدارة بسيطة.

### v1.8.2 — Plans and Limits

تعريف خطط وحدود واستهلاك مجمع دون تحصيل مالي، مع تنبيهات وحدود آمنة.

### v1.8.3 — Billing Preparation

استحقاقات وفترات وفواتير تجريبية وتسوية أحداث، دون تشغيل دفع حقيقي قبل المراجعة القانونية والمالية.

### v1.9.0 — Paid Beta

مجموعة مدارس محدودة، عقد وشروط ودعم ومراقبة، وربط دفع معتمد بعد إثبات العزل والتكلفة والطلب.

## بوابات قرار قبل التنفيذ

1. تحديد نموذج الهوية والمصادقة ومالك الحساب.
2. اعتماد تعريف tenant وملكية البيانات.
3. مراجعة قانونية وخصوصية وحقوق الأصول.
4. إثبات طلب من مدارس تجريبية ومشكلة مدفوعة واضحة.
5. ميزانية تكلفة ومراقبة ونسخ احتياطي ودعم.
6. نموذج تهديد ومراجعة مستقلة لعزل المستأجرين.

## درجة جاهزية SaaS الحالية

**3 من 10.**

توجد مكونات منتج وخادم وقاعدة بيانات وإدارة، لكنها تعمل دون هوية مستخدم أو عضوية أو عزل مستأجرين أو خطط. البداية الصحيحة ليست الدفع، بل تأسيس الهوية والعزل وملكية البيانات مع تجربة محدودة قابلة للتدقيق.
